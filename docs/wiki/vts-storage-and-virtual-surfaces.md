# VTS storage, aggregated driver, and virtual surfaces

See [index.md](index.md) for the wiki table of contents.

This document is VTS archaeology: it explains the server-side machinery
behind glues and virtual surfaces so that the concepts can be correctly
understood and eventually phased out. Cartolina's direction is to replace
this stack with client-side surface composition; understanding the legacy
is the prerequisite for a clean migration.


## The VTS storage

A VTS storage is a directory managed by vts-libs that contains three
kinds of objects:

- **Surfaces** — individual terrain tilesets, each stored as a
  standalone directory with its own `tileset.conf` and tile data.
- **Glues** — precomputed seam tilesets. A glue is itself a tileset
  directory, identified by the sorted list of surface IDs it stitches
  (e.g. `terrain-czech,viewfinder`). It contains mesh and texture data
  for the overlap area only.
- **Virtual surfaces** — aggregated composites. Each is also a tileset
  directory within storage, but its content is generated by the
  aggregated driver rather than stored independently. A virtual surface
  is registered in the storage's `storage.conf` properties alongside the
  list of surfaces it covers.

The storage is the deployment unit. vts-vtsd reads a storage and serves
it over HTTP. Cartolina-tileserver does not use VTS storage at all — it
serves surfaces independently and produces neither glues nor virtual
surfaces.


## The aggregated tileset driver

`AggregatedDriver` is one of several tileset driver types in vts-libs
(the others are plain, remote, local, etc.). It is identified by
`type: "aggregated"` in the tileset's `tileset.conf`. Its options
(`AggregatedOptions`, defined in `driver/options.hpp`) are:

- `storagePath` — relative path from the driver's root to the parent
  VTS storage.
- `tilesets` — the set of surface IDs that this composite covers.
- `tsMap` — a base64-encoded binary slot table (the same data served
  as `tileset.map` to the client).
- `surfaceReferences` — boolean: whether metatile nodes carry a
  `sourceReference` slot index (see below).
- `staticMetaRange` — LOD range for which metatiles are pre-baked on
  disk; metatiles above this range are synthesised on the fly.

The driver is not specific to virtual surfaces or to vts-vtsd. It lives
in vts-libs and is available to any vts-libs-based tool (vts-vtsd,
vts-tools, cartolina-tileserver). However, in practice it is only
instantiated by the virtual surface machinery described below.


## How a virtual surface is created

An administrator runs the `vts --command=vs-create` CLI tool
(implemented in `vts-libs/tools/vts.cpp:3511`) and names the surfaces to
aggregate. The tool calls `Storage::createVirtualSurface()`, which in
turn calls `aggregateTileSets()`. That function:

1. Reads the storage's constituent tilesets and resolves all glues that
   connect the named surfaces (`storage_.glues(tilesetId, ...)`).

2. Assigns each constituent (surface or glue) a slot index, starting
   at 1. Surfaces come first, then glues. Only one slot per glue is
   created regardless of how many surfaces it stitches.

3. Builds the unified tile index by merging each constituent's own tile
   index in slot order. The alien bit in the tile index flags is used
   internally as a filter during this merge (see
   [glue-alien-flag.md](glue-alien-flag.md)) but is not carried into the
   output.

4. Builds the **tsMap**: a binary table that maps each slot index to the
   set of surface IDs that identify the constituent (one ID for a
   surface; two or more IDs for a glue). This is the same table the
   client decodes as `tileset.map`.

5. Generates metatiles for the `staticMetaRange`. With the
   `sourceReferencesInMetatiles` flag set (always used for virtual
   surfaces via `AggregateFlags::sourceReferencesInMetatiles`), each
   MetaNode gets a `sourceReference` field — the 1-based slot index of
   the constituent that wins this tile address.

6. Writes all of this to a new tileset directory inside storage (the
   path is derived from the surface-ID list, e.g.
   `vs/terrain-czech_viewfinder/`).

The result is a fully self-contained tileset on disk: metatile binary
files plus `tileset.map`. The aggregated driver's `input_impl` method
knows how to serve them.


## How vts-vtsd exposes virtual surfaces

When vts-vtsd generates `mapConfig.json` for a storage request, it calls
`saveMapConfig()` (vts-libs). For each virtual surface in the storage's
`properties.virtualSurfaces` map, it calls `MapConfig::mergeVirtualSurface()`,
which appends a `VirtualSurfaceConfig` entry. The serialised JSON gains
a `virtualSurfaces` array:

```json
{
  "id": ["terrain-czech", "viewfinder"],
  "lodRange": [4, 21],
  "tileRange": [[0, 0], [13, 13]],
  "metaUrl": "../../vs/terrain-czech_viewfinder/{lod}-{x}-{y}.meta",
  "mapping": "../../vs/terrain-czech_viewfinder/tileset.map"
}
```

The `metaUrl` template points to the aggregated tileset's pre-baked
metatiles. The `mapping` URL points to `tileset.map` (the tsMap). No
other data from the aggregated tileset is served to the client — mesh
and texture data are still fetched from the individual surface and glue
tilesets referenced by `sourceReference`.


## The `sourceReference` field and the alien bit

These are two separate fields written into each metatile node by the
aggregated driver:

**`sourceReference`** (only when `surfaceReferences = true`). A 1-based
slot index into the tsMap. The client decodes it as "fetch mesh and
texture from this constituent." It is the server's precomputed answer to
the seam-stitching question. For a virtual-surface metatile, this is
always set.

**`alien`** — this bit is explicitly reset to zero for every node by
`MetaTile::update` (`metatile.cpp:860`). It is never set in any metatile
produced by the aggregated driver. See
[glue-alien-flag.md](glue-alien-flag.md) for the full story.


## Two generations of the aggregated driver

The aggregated driver was built in two stages:

**Generation 1 (pre-`virtualSurfaces`).**
The aggregated tileset was served as an ordinary tileset without any
`virtualSurfaces` declaration. The client treated it as a regular
surface-sequence entry. Metatile nodes had no `sourceReference`. The
intent was for the client's non-virtual stitching path
(`createVirtualMetanode`) to use the alien bit to resolve seam winners.
In practice the alien bit was never written into metatile output (see
[glue-alien-flag.md](glue-alien-flag.md)), so this mechanism was never
operational.

**Generation 2 (post-`virtualSurfaces`, current mapy.com).**
`sourceReferencesInMetatiles` was added. The aggregated tileset is
advertised via `mapConfig.virtualSurfaces`. The client collapses the
surface sequence to a single entry and reads `sourceReference` to
identify the winning constituent. `createVirtualMetanode` is never
called in this path.

Only generation 2 occurs in any known live deployment. Generation 1
behaviour is vestigial code in cartolina-js.


## Where each piece lives

| Component | Role |
|---|---|
| Component | Role |
| vts-libs | Storage format, `AggregatedDriver`, `aggregateTileSets()` |
| vts-tools | `vts vs-create` — calls `Storage::createVirtualSurface()` |
| vts-vtsd | Reads VTS storage; serves `mapConfig.json` and tile data |
| cartolina-tileserver | Independent surfaces; no storage, glues, or vs |
| cartolina-js | Parses `virtualSurfaces`; alien flag code inactive |


## Phase-out

The goal is to replace glues and virtual surfaces with a client-side
surface compositor that works at runtime without server pre-baking. The
full motivation, phase-out sequence, and relevant files are tracked in
[backlog.md](backlog.md) under "Replace glues and virtual surfaces with
client-side surface composition".
